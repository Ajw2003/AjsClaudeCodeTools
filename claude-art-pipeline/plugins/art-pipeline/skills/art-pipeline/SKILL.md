# Art pipeline: prompt to engine, and look at it every time

Proven on Ajw2003/PlunderSpell: 16 rigged enemies, 20 props, the player wizard and their clips,
all generated by Python in Blender, all reviewed by eye. `references/worked-example.md` is that
project's tooling, file by file, as a template to copy.

**The one rule.** Nothing made by code is done until someone has opened a picture of it beside
its concept and written down what they saw. A validator that passes says the numbers are legal
(closed mesh, under budget, right height). It cannot say the hat looks like a hat. The
`art-pipeline` plugin's Stop hook enforces this: a session cannot end while a model it changed has
no review sheet newer than the model, opened in this session, with a written verdict.

## The stages

Each stage ends at a gate: **open the image with the Read tool, compare, write what you saw.** A
fix is always followed by another look, never by the next stage.

```
0 protect → 1 brief + style bible → 2 concept → LOOK → 3 spec → 4 model → LOOK
          → 5 rig + pose test → LOOK → 6 clips → LOOK → 7 engine import → LOOK in engine → 8 commit
```

| Stage | Produces | Gate (what to look for) |
|---|---|---|
| 0. Protect | an autosave or frequent commits on your own branch | — |
| 1. Brief + style bible | `docs/art/BRIEF.md` from `references/style-bible-template.md`: register, palette, scale, budgets, sheet conventions | the user approves it; nothing is drawn before |
| 2. Concept | one sheet per asset, drawn by code (SVG or Pillow), rendered to PNG; an HTML proposal page when the user must choose | scale against the reference human; colours only from the bible; no overlapping labels; the user approves designs that are theirs to decide |
| 3. Spec | one JSON entry per asset: dimensions, materials with hex, build bullets with real sizes, budget, rig and clip list | numbers on the sheet equal the numbers in the JSON |
| 4. Model | mesh, baked textures, FBX/glTF/.blend, built by a blueprint script; a validator | review sheet: concept left, renders right (¾, front, side, wireframe); silhouette, proportion, colour, budget on the caption |
| 5. Rig | armature with engine-standard bone names, skin weights, a test pose | posed views bend without tearing; props follow the hands; nothing below the floor |
| 6. Clips | in-place keyframed clips exported per family; metrics (foot slide, lowest point, events) | 8 stills per clip on the actual model plus an MP4; feet do not slide; the pose reads as the action |
| 7. Engine | importer rules in code (rig type, loop flags, materials), a generated animator, a driver script | a screenshot or capture in the engine; the user checks what this machine cannot run |
| 8. Commit | everything above, including every sheet and render | `git status` clean; docs tier updated |

Full detail per stage, with commands: `references/stages.md`.

## How to work through it

0. **One ledger per asset, one loop.** `python "${CLAUDE_PLUGIN_ROOT}/scripts/art.py" new <slug>
   --kind prop|character|creature|set`, then loop: `art.py next <slug>` (prints the stage, what it
   produces, the gate and the exact commands) -> do the stage -> `art.py record` -> `art.py advance`.
   Stages: brief, concept, spec, model, rig, clips, engine, done (rig/clips are n/a for prop/set).
   brief and concept need `--approved-by-user`; the rest are look gates needing `--sheet` (opened with
   Read this session, newer than the stage's outputs) and `--seen` (>= 40 chars), and a pass needs at
   least `min_looks` (default 2) records, so one fail -> fix -> look cycle. The only ways round a
   gate are `art.py skip <slug> --reason "..."` and `--first-look-pass "<reason>"`; both are listed
   with their reason at every Stop. `art.py status` shows all assets.
1. **Read the project first.** Find its art docs, scale doc and any existing forge before writing
   one. Extend what is there; the worked example shows the shape when nothing is.
2. **Decisions that are the user's go to the user**, with a proposal page or a question: the look,
   anything that contradicts an approved plan (for example a death animation when the plan says the
   body vanishes). Defaults that are just craft, you choose and say so.
3. **Set up Blender as a Python module**: `sh scripts/setup_bpy.sh` (from this skill's folder).
   It finds a Python that matches a `bpy` wheel and installs it with Pillow. Cycles uses the GPU when present, CPU in GPU-less containers:
   EEVEE and Workbench still abort without a GPU. `references/tooling-and-traps.md` has the rest.
4. **Build by blueprint, never by hand-edit.** Fix the generator, not its output, so a rebuild
   keeps the fix. Every output is regenerable from a committed script and spec.
5. **Render and compose the review sheet** for every model you touch:

   ```bash
   python3.11 scripts/render_views.py <model.fbx|.glb|.blend> --out <dir>
   python3 scripts/review_sheet.py --concept <concept.png> --views <dir> --title "<Name>" --out <sheet.png>
   ```

   Projects with their own renderer (PlunderSpell's `render.py`) use it instead; the gate only
   cares that a fresh sheet exists and was opened.
6. **Look.** Open the sheet with Read. Compare it with the concept, and write down what you saw:
   what matches, what does not, what you will change. Change, rebuild, re-render, look again. At
   least one improvement pass per asset; "it passed" is not a look.
7. **Record the look** so the gate can see it:

   ```bash
   python "${CLAUDE_PLUGIN_ROOT}/scripts/review.py" record --model <model path> --sheet <sheet.png> \
       --verdict pass --seen "<what you saw, at least 40 characters>"
   ```

   `--verdict waived` (with the reason in `--seen`) is for a model that genuinely cannot be
   rendered here; it is reported, never silent. `python "${CLAUDE_PLUGIN_ROOT}/scripts/review.py"
   status` lists what the gate will say before you stop.
8. **Keep the docs in step with the art.** Docs that describe art (a scale doc's roster, a brief's
   budgets, a tool's status line) drift the moment a roster changes. Give the project a drift check
   (a script comparing docs with the data and code, see `references/stages.md`, stage 8) and name it
   in `.art-pipeline.json` at the repo root, so the gate runs it before every stop that changed a
   model or a doc:

   ```json
   {"doc_check": "python3 Tools/docs/check_art_docs.py", "doc_check_paths": ["docs/**", "**/*.json"]}
   ```

   The same file can set `model_globs`, `exclude` and `review_dir` (default `docs/art/reviews`).
9. **Engine work you cannot run here is UNTESTED**, said plainly, with the exact menu item or
   command the user runs and what they should see.

## Delegating

Concept and model work splits cleanly per asset: one worker per asset family, each with a saved
brief in the repo (so a worker cut off by a usage limit can be resumed) and its own paths. Workers
look at their own sheets; the coordinator looks again before committing. Never more than two
workers at once on one checkout, and each stages only its own paths.
